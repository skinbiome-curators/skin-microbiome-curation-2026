# 검수 기준과 지시문 — 문서 오류가 아니라 프로젝트의 결함을 찾는 검수

**작성:** 2026-10-17 · **대상:** 2조 팀원 · Claude(다음 세션) · **성격:** 기준 — 검수할 때마다 이 문서를 따른다. 고치면 아래 «바뀐 것»에 적는다.
**왜 만들었나:** 사용자 질문(10/17)에서 출발했다. *'단순히 문서 오류를 찾는 게 아니라, 이 프로젝트에 결함이 없는지 · 제대로 따지면서 진행했는지 · 고려하지 못한 게 있는지 · 한계점을 고려하면서 진행하는지 검수하고 싶다.'*

---

## 1. '잘 검수했다'고 말할 수 있는 기준

검수가 꼼꼼했는지는 느낌으로 판단하지 않는다. 다음 다섯 가지를 **보여 줄 수 있어야** 잘한 검수다.

| 기준 | 보여 주는 것 |
|---|---|
| **범위** | 무엇을 봤고 **무엇을 안 봤는지** 목록이 있다. '문제없음'으로 끝난 항목도 적혀 있다 |
| **근거** | 지적마다 원문 · 원자료 · 코드 줄을 가리킨다. 우리 해석은 '추론'이라고 표시하고, 확인 못 한 것은 ❌ 로 둔다 |
| **독립성** | 만든 사람의 결론을 모르는 쪽이 검수했다. 검수자에게는 대상 파일과 원자료 위치만 준다 |
| **잡아내는 힘** | 검수 전에 몰래 심은 오류를 몇 개 잡았는지로 잰다(5-1) |
| **마무리** | 모든 지적이 '고침 · 사용자 결정 · 한계로 기록' 중 하나로 닫혔다. 열린 지적이 없다 |

## 2. AI 검수가 얕아지는 이유 — 이 프로젝트에서 실제로 있었던 일

| 약점 | 있었던 일 |
|---|---|
| 문서끼리만 맞추고 원자료와 대조하지 않는다 | 15계절 '미국·중국 가구'는 9/19 부터 틀려 있었다. 10/8 검수는 data 의 ethnicity = Chinese 를 보고도 '모순 아님'으로 넘어갔다. 10/17 에 ENA 원본(country = Hong Kong)을 열고서야 잡혔다 |
| 만든 쪽이 깐 전제는 만든 쪽이 의심하지 못한다 | 10/16 장(분변) 근거를 피부 시장 근거로 바꿔 쓴 것은 사용자가 잡았다(`../references/피부측정문제_원문확인_20261016.md` 머리) |
| 뜻을 말없이 바꾼다 | 10/17 결정 문장의 '반복'(반복측정)을 규칙 문서에서 '2주 · 4주 방향 일치'로 바꾸고 알리지 않았다(`../경진대회/효능판정기준_초안_261017.md` ★ v1 → v2) |
| 지시문에 넣은 추측을 검수자가 그대로 옮긴다 | 10/8 '1회차 9/29 · 2회차 9/30' 추측이 검수 결과에 그대로 들어갔다 |
| 쉬운 오류만 많이 찾고 끝났다고 느낀다 | 오타 · 숫자 오류는 찾기 쉽다. '질문 자체가 맞나' 같은 틀의 오류는 따로 묻지 않으면 찾지 않는다 |
| 권고하는 쪽으로 결정이 기운다 | 10/17 효능 판정의 사용자 결정 8개가 모두 Claude 권고안이었다. 선택지를 짠 판단이 사실상 설계를 정했다 |

**AI 검수끼리는 맹점이 겹친다.** 그래서 팀원 검수와 외부 피드백(멘토 · 심사위원)을 대신하지 못한다.

## 3. 검수의 층 — 층마다 따로 묻고 따로 돌린다

'오류를 찾아 줘'라고만 하면 ①층만 한다.

| 층 | 묻는 것 | 방법 |
|---|---|---|
| ① 사실 | 숫자 · 인용 · 출처가 원문과 같은가 | 주장 목록을 만들고 원문 · 원자료와 하나씩 대조한다(문서끼리 대조는 대조가 아니다) |
| ② 추론 | 근거에서 결론으로 가는 고리가 이어지는가 | 핵심 주장마다 '주장 → 근거 → 추론 단계'를 표로 펼쳐 끊긴 고리를 찾는다 · 근거보다 센 말을 찾는다 |
| ③ 방법 · 설계 | 그 선택이 정당한가, 다른 선택지를 따졌는가 | 결정마다 대안 · 반대 근거 · '대안을 골랐다면 결과가 달라지나'를 따진다 |
| ④ 전제 | 프로젝트가 기대는 가정은 무엇이고, 틀리면 어떻게 되나 | **가정 목록 감사** — 가정 · 근거 · 틀리면 무너지는 것 · 시험 방법 |
| ⑤ 빠진 것 · 한계 | 고려하지 못한 것, 한계를 알고 진행했나 | **사전 부검** — '발표가 실패했다고 가정하고 이유를 쓰라' · 아래 관점별로 검토한다 |
| ⑥ 검수의 검수 | 이번 검수가 제대로 찾았나 | **심은 오류**를 몇 개 잡았는지 본다(5-1) |

**⑤에 쓰는 관점(이 프로젝트에 맞춤):**
- 경진대회 심사위원(10/10 안내문의 확인 항목)
- 고객(중소 화장품사 R&D 담당자)
- 규제(식약처 실증 · 광고 규정)
- 통계 리뷰어
- 피부 미생물 연구자
- 회의론자('이 사업은 필요 없다'고 주장하는 쪽)
- 처음 보는 팀원

## 4. 지시문 — 그대로 붙여 쓴다

'찾아 줘'가 아니라 **'깨뜨려 봐'**로 묻는다. 만든 사람의 결론은 검수자에게 주지 않는다. 출력 형식을 정하고, 안 본 것도 적게 한다.

```
[검수 지시]
대상: (예: 경진대회/ 전체 + 그 근거 문서 · 또는 프로젝트 전체)
목적: 다음 발표 전에 이 프로젝트의 결함을 찾는다. 문서 오류는 ①층일 뿐이다.

규칙
1. 층을 나눠 따로 검수한다: ①사실 ②추론 ③방법·설계 ④전제 ⑤빠진 것·한계
2. 검수 에이전트에게 만든 쪽(Claude)의 결론·추측을 주지 않는다. 대상 파일과 원자료 위치만 준다.
3. 근거는 원문·원자료·코드 줄만. 해석은 '추론'으로 표시. 확인 못 한 것은 ❌.
4. '문제없음'도 결과다. 본 항목·안 본 항목을 모두 적는다.
   지적 수를 채우려고 억지 지적을 만들지 않는다.
5. ④는 가정 목록 표로: 가정 | 근거 | 틀리면 무너지는 것 | 시험 방법
6. ⑤는 사전 부검 + 관점별(심사위원·고객·규제·통계·미생물·회의론자·새 팀원)로.
7. 지적마다: 위치 | 무엇이 문제 | 왜(근거 종류) | 심각도(치명/중요/사소) | 고칠 것 또는 '사용자 결정 필요'
8. 나온 지적은 다른 에이전트가 반박을 시도해 거른다(거짓 지적 줄이기).
9. 검수 전에 검수자가 모르게 오류 3–5개를 심고, 몇 개 잡혔는지 마지막에 보고한다.
10. 끝: 모든 지적을 '고침 / 사용자 결정 / 한계로 기록' 중 하나로 닫는 표.
    코드·문서 수정은 그 표를 사용자가 본 뒤에.
```

## 5. 실행 절차

### 5-1. 심은 오류 — 실제 파일은 건드리지 않는다

1. 검수 대상 문서의 **사본**을 저장소 밖(Claude 세션의 임시 폴더)에 만든다.
2. 사본에 오류 3–5개를 심는다. 층마다 하나씩 고루 심는다.
   - 사실: 숫자 하나를 바꾼다
   - 인용: 원문 인용 속 숫자를 바꾼다
   - 추론: 근거보다 센 문장을 넣는다
   - 방법: 공식 하나를 바꾼다
   - 전제: 다른 영역(장) 근거를 피부 근거처럼 넣는다
3. **심은 오류 목록은 검수자가 볼 수 없는 곳에 둔다.** 검수자에게는 '대상 문서는 사본만 본다 · 저장소의 같은 파일은 열지 않는다'고 지시한다.
4. 검수가 끝나면 목록과 대조해 **몇 개 잡혔는지**를 보고에 적는다. 잡히지 않은 오류가 있으면 그 층의 검수가 약했다는 뜻이다.
5. 심은 오류는 사본에만 있다. 검수 지적 중 심은 오류에 해당하는 것은 실제 문서에 반영하지 않는다.

### 5-2. 구성 — workflow(여러 에이전트)로 돌릴 때

| 단계 | 에이전트 | 하는 일 |
|---|---|---|
| 검수 | 6개(동시) | ① 사실 · ② 추론 · ③ 방법 · 설계 · ④ 전제 · ⑤-가 사전 부검(심사위원 · 고객 · 새 팀원) · ⑤-나 관점 검토(규제 · 미생물 · 통계 · 회의론자) |
| 반박 검증 | 2개 | 검수 지적마다 반박을 시도한다. 원문으로 확인되면 '확인', 반박되면 '기각', 판단이 서지 않으면 '보류' |
| 정리 | 1개 | 중복을 합치고, 심각도 순으로 정리하고, '고침 / 사용자 결정 / 한계' 중 하나로 분류 |

- **비용:** 에이전트 하나가 대략 13–18만 토큰이다(10/17 기준). 9개면 약 100–150만 토큰이다. 단 이 범위를 처음 검수할 때는 문서마다 원문을 찾아가느라 검수 에이전트 하나가 30만 토큰 안팎을 썼다(10/17).
- workflow 는 사용자가 명시적으로 요청할 때만 돌린다.
- **반박 검증은 한 에이전트가 20개 이하만 맡는다.** 10/17 첫 검수에서 지적이 70개를 넘었다. 2개가 나눠 맡기에는 많다.
- **반박 검증을 더 세게 시킨다.** 10/17–18 검수에서 반박 검증이 118건 중 116건을 '확인'했다(98%). 반박을 충분히 시도하지 않았을 수 있다. 다음에는 이렇게 지시한다.
  - 기본값은 '보류'로 둔다. 직접 연 원문 근거를 evidence 에 적을 때만 '확인'으로 한다.
  - 지적마다 반박 시도를 한 줄 이상 적게 한다.
  - 만든 쪽(Claude)이 지적 몇 줄을 직접 원본과 대조해, 검증 판정이 맞는지 표본으로 본다(10/18 에는 3줄 · 3줄 모두 맞음).
- **① 사실 층은 원문까지 가게 따로 돌리고, 범위를 나눈다.** 10/18 심은 오류 S2(인용 속 숫자)는 원문 전문을 연 사실 검수 하나만 잡았다. 문서끼리 맞춰 보는 다른 층은 모두 놓쳤다. 사실 검수는 무거워서 세션 한도에 두 번 걸렸다. 그래서 문서 묶음별로 나눴다.
- **중간에 끊겼을 때(세션 한도 등):** 이어 돌리기는 '앞에서부터 바뀌지 않고 끝난 호출'까지만 저장 결과를 쓴다. 맨 앞 호출이 실패했으면 끝난 것까지 전부 다시 돈다. 10/17 에 그렇게 검수 4개를 다시 돌리다 멈췄다. 그때는 이렇게 한다.
  1. 기록(journal)에서 끝난 결과를 꺼내 파일로 둔다.
  2. 남은 것만 돌리는 새 스크립트를 쓰고, 끝난 결과는 그 파일 경로로 넘긴다.
